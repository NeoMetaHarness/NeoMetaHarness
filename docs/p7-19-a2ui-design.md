# P7-19 · Interactive agent UI with A2UI

Design for PM approval. Implementation starts after approval.

## Engine transport

Use a line-delimited `a2ui` Markdown fence containing a JSON array of A2UI v1.0 agent-to-renderer messages. Supply the same short Neo catalog description, example and action format to both engines on opt-in turns. Keep the original assistant text, including fences, in the engine transcript. The Gateway derives ordered text and surface segments only from successful, completed assistant messages. User messages, tool results and reasoning events stay outside this path. Malformed, incomplete, oversized or unsupported blocks remain plain text.

| Option | Decision and evidence from the pinned sources |
| --- | --- |
| Hermes instructions or skill | Use per-run `instructions` on `POST /v1/runs`. In `hermes-agent@v0.23.2/gateway/platforms/api_server_runs.py`, `_resolve_chained_history` reads `instructions`, run preparation passes it as `ephemeral_system_prompt`, and the text callback emits SSE `message.delta`. `tools/skills_tool.py` also supports `SKILL.md` discovery and `skill_view`, which depends on model selection of the skill. The fork's `skills/a2ui/SKILL.md` targets developers integrating A2UI. Use it as a reference for the smaller Neo instruction. |
| T3 provider instructions or skills | Use the opt-in turn's `message.dispatch` text to carry the instruction alongside the prompt. `t3code@v0.1.9/packages/contracts/src/orchestrationV2.ts` defines the dispatch command, `orchestration.subscribeThread` and assistant `message.updated`. `apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts` handles `item/agentMessage/delta`. The dispatch contract has no provider-neutral system instruction field. Provider-specific files and skill installation would vary by agent. The instruction is visible in T3's stored user message. |
| Fenced assistant text | Use this as the common carrier. It works over existing text seams with both engines and gives a textual transcript when Neo disables the extension. Keep parsing and catalog validation in Neo. |
| `@a2ui/catalog-mcp` | Defer. The fork's `typescript/catalogs/mcp/README.md` describes `callMcpTool` and `McpApp`, which let a surface call tools and open MCP Apps. They require a host MCP client and do not deliver A2UI messages from ordinary Hermes and T3 assistant streams. Keep controls on the Neo conversation action path. |

The current Agents page uses `x.engine-hermes.runs` directly. Its wrapper sends `{ input }` to Hermes, and a profile alone does not resume the same conversation. Add an internal wrapper path for `instructions`, `session_id` and run status. Resolve the effective session via `GET /v1/runs/{run_id}` using the original profile and the server-recorded run ID. The chat host owns that binding so ordinary follow-ups can keep using the same session after the extension is disabled. The pinned `api_server_runs.py` selects `session_id`, loads its conversation history and can resolve a rotated session. For Coding, `engine-t3/src/client.ts` already dispatches messages to the existing thread and converts assistant `message.updated` into full-text revisions. Both engine integrations stay within the [registered seams](../upstream/registry.yaml).

## Gateway and rendering

- Add `extensions/a2ui/neo.extension.json` with a Cordis service and an App contribution for assistant message bodies. Use optional hooks at the existing Gateway chat handlers and Agents/Coding message views. Either engine can be absent. The checked-in App has no general UI slot loader, so use a narrow, lazy-loaded contribution for this bundled feature and keep feature logic in the extension.
- Keep the Gateway's 33 ms coalescing and `StreamView`'s imperative text updates. While a turn streams, retain bounded per-message text outside React state. Append Hermes deltas and replace T3 full-text revisions. On successful completion, validate the final text and hand the App an ordered set of text and surface segments. Reconcile T3 snapshots using their authoritative messages and stable turn/message identities. Replayed revisions never duplicate surfaces. Enabled views may buffer a candidate fence until completion and flush it as ordinary text on rejection or interruption. React receives completed segments and normal widget input state.
- Use the pinned `@a2ui/web_core` `MessageProcessor` and surface/data models with one local Neo catalog. Start with text, heading, grouping, button, checkbox and labeled text input. Render through `@neometaharness/ui`, exporting missing Astryx primitives from that package as needed. Let the parent app supply the P7-18 theme and semantic colors, spacing and focus tokens. Use the same widgets and keyboard behavior in light and dark modes and in desktop, web and PWA.
- On disable or unload, unregister action dispatch and clear pending surface state and grants. Show the original transcript through `StreamView`, including for messages already mounted. Preserve normal chat, history, approvals and stop controls. Bundled UI assets load only when the extension is active.

## Actions and validation

- A visible user click or form submit sends the renderer action to `x.a2ui.action` with an opaque action handle, an idempotency key and only the fields declared for that control. The Gateway resolves the handle to the authenticated user/workspace, conversation, source message, surface revision and component. Recheck the member policy and conversation access, reject stale or replayed actions and serialize with normal sends. Mint handles from authorized server-observed output. The client never supplies the engine target. The Gateway serializes the validated v1.0 action as a user-turn payload, returns the normal chat handle, and reuses Hermes `POST /v1/runs` with the bound session or T3 `message.dispatch` with the bound thread. Existing engine tool-approval paths still apply.
- Add an explicit contract and central policy entry. The existing T3 send and stream handlers check roles and pass the thread ID through directly. The Agents page likewise uses profile-level engine routes. For server mode, record workspace ownership for A2UI-enabled conversations through their authenticated creation flow. Keep actions unavailable for existing conversations whose ownership Neo cannot establish and for viewers. Test cross-workspace access even when someone knows a valid upstream ID. Unverified replayed history may display a surface with inactive controls.
- Validate the v1.0 `specification/v1_0/json/agent_to_renderer.json` and `renderer_to_agent.json` envelopes and the local catalog before processing. Reject unknown properties and widgets, foreign catalogs, executable markup, arbitrary styles, scripts, remote resources, agent functions, MCP and invalid graph or data bindings. Bound payload bytes, messages, surfaces, components, depth and field sizes. Check schema limits and graph references before mounting anything. Validate visible submitted fields against the approved action definition server-side.
- No remote media in the initial catalog. Neo renders a bounded Markdown subset directly as React elements (paragraphs, emphasis, strikethrough, quotes, lists, code and hard breaks). Links, images and raw HTML remain inert text. Text is limited to 4,096 characters and eight levels of parsing.

## Plan compatibility

P7-19 explicitly names this fork. Architecture §13's source-repository rule applies to engines, and the registry should identify A2UI as a library dependency. PRD APP-1 and APP-5 fit the shared Astryx UI and P7-18 themes. ADR 0001 keeps the Tauri shell out of the feature, ADR 0002 keeps the action behind Neo's typed Gateway, ADR 0004 governs extension lifecycle, ADR 0005 requires the action authorization checks, and ADR 0003 governs any persisted conversation bindings. The two implementation gaps are the App contribution seam and authenticated conversation bindings in server mode.

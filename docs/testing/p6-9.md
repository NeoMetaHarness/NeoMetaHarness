# P6 exit scenarios

`pnpm test:p6-9` builds the App first and uses a desktop-token authenticated
Gateway, isolated T3/DSH/Hermes homes, scripted models, fake WhatsApp and GitHub,
and the fake computer provider. It performs no pushes or GitHub writes.

## Scenarios

1. An App request delegates coding to `neo-coding` through T3, creates a worktree,
   edits a feature using DSH, and prepares a local branch, commit and PR description.
   A read-only GitHub query confirms an open PR for that exact branch and commit
   before the report says the PR is up. The fake endpoint only confirms a PR after
   the real local commit exists. WhatsApp receives the report through its bridge.
2. A Monday cron routine delegates research to a Hermes bot assigned a fake
   computer. Its real MCP screenshot call reaches the computer registry and its
   report appears in the App Inbox. The authenticated cron fire route advances
   execution without waiting for Monday.
3. An explicit remember request writes global user memory through Neo's memory
   interface. A later Hermes turn and a separate DSH session recall that fact.
   Private bot memory filters remain unchanged.

Restart assertions cover persisted reports, routines, coding threads and delivery
acknowledgements. Acknowledged WhatsApp notifications must not replay. Disabling
superagent leaves other extensions healthy.

## Production integration fixes

- Install Hermes' optional MCP dependencies and initialize/close discovered MCP
  clients from Neo's bridge.
- Expose coding and explicit memory tools in the superagent MCP bridge, consume
  the last workflow tool result, and require actual GitHub evidence for PR claims.
- Resolve App WhatsApp destinations against connected profiles, bot ownership and
  admitted recipients. Persist delivery status and retry pending delivery on boot.
- Require a live channel transport before recording notification delivery.
- Remove destination resolution before HTTP method/input validation when Channels
  is disabled, so it follows the Gateway availability contract.

The new destination route requires a member; the read-only configured-repository
PR confirmation route requires a viewer. Both are in `CONTRACT_POLICY`. No engine
source is changed. Coding uses the existing admin-registered ACP provider.

# P6 exit integration probe

`pnpm test:p6-9` builds the App first, boots an authenticated desktop Gateway in
an isolated temporary data directory, and uses scripted models and a fake computer.
This is an incomplete exit test: it deliberately reports failure while exit
requirements remain unimplemented. Do not count its component PASS lines as a
P6 exit PASS. No real subscriptions, user desktops, pushes or GitHub writes run.

## Verified coverage

- A real Monday cron routine fires the superagent, which delegates to a real
  isolated Hermes bot. The bot executes the projected MCP screenshot tool against
  `computer-fake`, resumes from its tool result, and reports to the Inbox.
- The built App displays that Inbox report.
- A second request, submitted through the App composer, produces an engine memory
  write. A later real DSH turn exercises the memory context plugin.
- After a Gateway restart the completed report, routine and bot remain present.

The cron clock is advanced using the existing authenticated `inbox.cron.fire`
route; this avoids waiting for Monday and does not replace cron execution.

## Remaining exit blockers

1. **Coding delegation is absent.** Live stdio `tools/list` from the production
   superagent bridge exposes `agents.send_to_bot` only
   (`extensions/engine-superagent/src/mcp-server.mjs:17`). Worker instructions
   require that exact Hermes delegation (`src/model.ts:34`). No worker tool starts
   a T3/DSH coding task or calls local PR preparation. The scenario-1 fixture and
   fake GitHub/WhatsApp chain are therefore not implemented or claimed as tested.
2. **App-origin WhatsApp notifications have no destination contract.**
   `packages/contracts/src/index.ts:601` accepts text, bot and mode only.
   Reply destinations are registered exclusively by inbound channel messages
   (`extensions/engine-superagent/src/index.ts:284-292`). The existing WhatsApp
   delivery seam is `extensions/channels/src/index.ts:387`. A completed local PR
   preparation must also remain distinct from an externally published PR; the
   fake GitHub lifecycle still needs an explicit production integration path.
3. **Engine writes do not cross profile boundaries.** The real Hermes remember
   turn persists Z as `hermes.turn`. A new DSH session in the same workspace
   receives no Z in its actual model request. Writes use the originating profile
   (`apps/gateway/src/server.ts:1185`), while recall accepts only `global` or the
   consuming profile (`:1160`). A shared-memory write/promotion path is needed;
   dropping that scope filter would disclose unrelated bot memory. This probe
   does not weaken the filter or copy records manually to manufacture success.

The scope question sent to the PM asks whether to implement these missing
capabilities within P6-9 or return them to their owning tasks. Until resolved,
the exit remains blocked. No readiness file is edited. No new routes are added,
so there are no policy entries to add in this diagnostic step.
